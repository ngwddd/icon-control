# v1.4.3 计划：先测量，再优化

来源：两轮外部评审 + 代码核对。**不新增 MCP 工具**，只改实现与参数。

## 一、两轮评审最终采纳的结论

| 议题 | 结论 |
|---|---|
| "UIA 缓存" 排第一 | **延后**。`uiautomation 2.0.29` 不暴露 `CacheRequest`；要用得自己包 `IUIAutomation::CreateCacheRequest`，属于替换观察后端，不是小改动。没有实测数据前不投入。 |
| "改用 TreeWalker" | **撤销我上一轮的说法**。已核实 `uiautomation.Control.GetChildren()` 本身就是 `GetFirstChildControl()` + `GetNextSiblingControl()` 的 Walker 循环。手动改写只省 Python 列表与"父节点宽列表"的剩余枚举，不是把跨进程调用变一次。 |
| OCR `ratio` 默认 1.0 | **是真缺陷，但当前正常路径不触发**：`ocr_ext.find_text()` 每条命中都写 `"ratio": round(ratio,3)`。按"防御缺陷"修，不能算作准确率提升的证据。 |
| `ui_query` 新增工具 | **不新增**：`ui_find` 加条件参数即可。 |
| CDP 浏览器直连 | **延后**：只对浏览器有效，当前主要场景是微信/游戏。 |
| 视觉跟踪 | **提前到 R2**，用 cv2（已装 5.0）+ `match_template`，不需要视觉模型。 |
| 增量快照 | **只省传输，不省底层遍历**。真正省时间要事件/子树缓存，属于 R3 之后。 |
| RuntimeId | **不能单独作长期身份**。按"实例→重建→重排→歧义"分级匹配。 |
| 多区域共享帧 | 不一律整屏：比较"整屏 / 联合矩形 / 分别采集"三者耗时与字节数再定。 |

## 二、阶段与交付物

| 阶段 | 内容 | 交付 | 验收 |
|---|---|---|---|
| **R0** | 基准设施 | `tools/bench/observe_bench.py`（微基准）、`tools/bench/task_bench.py`（固定任务集）、基线 JSON | 能回答"时间花在遍历还是属性读取"、"每个任务的 OCR 次数与调用数" |
| **R1** | 低风险优化 | OCR 默认分修正、`automation_id` 按需读取、`ui_find` 条件查询、宽父节点早停 | 前后同任务对比：UIA 属性读取次数、观察耗时、调用数 |
| **R2** | 视觉跟踪 POC | `match_template` 增加 `search_region` / `previous_ref` / `tracking_mode`；跟踪生命周期与失效拒绝 | 目标移动能跟；目标消失/歧义时**拒绝**而不是乱点 |
| **R3**（按数据决定） | 增量 `ui_tree(mode=delta)` | 身份配对（RuntimeId→AutomationId+父级→路径+相邻） | 只省传输时如实标注"不省底层耗时" |
| **不做** | UIA 原生缓存、CDP、视觉模型、`ui_read_table` | — | 由 R0 数据决定是否重新排期 |

## 三、R0 的测量口径

**微基准**（回答优化方向）：
1. 同一窗口 `ui_tree` 总耗时，拆成「遍历」与「属性读取」两部分。
2. 每个节点分别读 1/2/3/4 个属性的成本（验证 AutomationId 的代价）。
3. 宽父节点（列表）下，`GetChildren()` 全量枚举 vs 达到 `max_nodes` 就停的差异。

**任务集**（回答真实收效）：
| 场景 | 任务 | 独立判据 |
|---|---|---|
| 资源管理器 | 找到指定文件并读取大小 | 文件系统实际大小 |
| 记事本 | 定位编辑区、输入、回读 | 控件 `Value` 或 OCR |
| Windows 设置 | 找到指定开关并读状态 | 控件 `ToggleState` |
| 微信聊天 | 找到指定聊天 | 截图人工/OCR 复核 |
| 微信朋友圈 | 定位重复图标 | 截图复核 |
| 游戏/HUD | 跟踪一个目标 | 截图复核 |

每个任务记录：调用数、OCR 次数、UIA 读取次数、P50/P95 耗时、是否一次成功、失败重定位次数。**完成与否不看 `success=true`**，看上面第三列。

## 四、原则

每个阶段必须证明至少改善一项：准确率 / 执行延迟 / 调用数 / OCR 次数，且不显著损害其他项。做不到就回滚，不写进发布说明。

## 五、R0 基线（2026-11-14，本机 2560×1440）

`tools/bench/observe_bench.py`，depth 8，max_nodes 400，9 次取中位数。同一份 `_walk` 复制品，
分别只读 0/1/2/3/4 个属性，把"遍历"和"属性读取"拆开。

| 窗口 | 节点 | 纯遍历 | 全量读取 | 遍历占比 | 属性占比 |
|---|---|---|---|---|---|
| 资源管理器 | 279 | 78.4 ms | 129.9 ms | **60%** | 40% |
| 记事本 | 131 | 41.3 ms | 60.8 ms | **68%** | 32% |

单属性成本（资源管理器，279 节点）：Name +16.4 ms、BoundingRectangle +14.1 ms、
ControlTypeName +10.4 ms、**AutomationId +10.6 ms**。

宽父节点（29 个子项）：`GetChildren()` 5.09 ms，walker 只取前 10 个 3.44 ms（省 1.65 ms）。

### 结论

1. **遍历是大头（60–68%）**，只缓存属性最多解决四成——这正是"原生缓存先延后、但别指望属性优化翻倍"的数据依据。
2. **`AutomationId` 按需读取值 ~8%**（10.6 / 135.7 ms），低风险，先做。
3. **宽父节点早停**在小列表只省 1.6 ms，但按子项线性放大：500 项的列表约省 30 ms。
4. `ui_tree` 实测 135.7 ms，复制品 129.9 ms，误差 4%，可以拿复制品做 A/B。

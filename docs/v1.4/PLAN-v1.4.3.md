# v1.4.3 计划：先测量，再优化

来源：两轮外部评审 + 代码核对。**不新增 MCP 工具**，只改实现与参数。

## 一、两轮评审最终采纳的结论

| 议题 | 结论 |
|---|---|
| "UIA 缓存" 排第一 | **延后**。`uiautomation 2.0.29` 不暴露 `CacheRequest`；要用得自己包 `IUIAutomation::CreateCacheRequest`，属于替换观察后端，不是小改动。没有实测数据前不投入。 |
| "改用 TreeWalker" | **撤销我上一轮的说法**。已核实 `uiautomation.Control.GetChildren()` 本身就是 `GetFirstChildControl()` + `GetNextSiblingControl()` 的 Walker 循环。手动改写只省 Python 列表与"父节点宽列表"的剩余枚举，不是把跨进程调用变一次。 |
| OCR `ratio` 默认 1.0 | **是真缺陷，但当前正常路径不触发**：`ocr_ext.find_text()` 每条命中都写 `"ratio": round(ratio,3)`。按"防御缺陷"修，不能算作准确率提升的证据。 |
| `ui_query` 新增工具 | **不新增**：`ui_find` 加条件参数即可。 |
| CDP 浏览器直连 | **延后**：只对浏览器有效，当前主要场景是微信/游戏。 |
| 视觉跟踪 | **提前到 R2**，用 cv2（已装 5.0）+ `match_template`，不需要视觉模型。 |
| 增量快照 | **只省传输，不省底层遍历**。真正省时间要事件/子树缓存，属于 R3 之后。 |
| RuntimeId | **不能单独作长期身份**。按"实例→重建→重排→歧义"分级匹配。 |
| 多区域共享帧 | 不一律整屏：比较"整屏 / 联合矩形 / 分别采集"三者耗时与字节数再定。 |

## 二、阶段与交付物

| 阶段 | 内容 | 交付 | 验收 |
|---|---|---|---|
| **R0** | 基准设施 | `tools/bench/observe_bench.py`（微基准）、`tools/bench/task_bench.py`（固定任务集）、基线 JSON | 能回答"时间花在遍历还是属性读取"、"每个任务的 OCR 次数与调用数" |
| **R1** | 低风险优化 | OCR 默认分修正、`automation_id` 按需读取、`ui_find` 条件查询、宽父节点早停 | 前后同任务对比：UIA 属性读取次数、观察耗时、调用数 |
| **R2** | 视觉跟踪 POC | `match_template` 增加 `search_region` / `previous_ref` / `tracking_mode`；跟踪生命周期与失效拒绝 | 目标移动能跟；目标消失/歧义时**拒绝**而不是乱点 |

| **不做** | UIA 原生缓存、CDP、视觉模型、`ui_read_table` | — | 由 R0 数据决定是否重新排期 |

## 三、R0 的测量口径

**微基准**（回答优化方向）：
1. 同一窗口 `ui_tree` 总耗时，拆成「遍历」与「属性读取」两部分。
2. 每个节点分别读 1/2/3/4 个属性的成本（验证 AutomationId 的代价）。
3. 宽父节点（列表）下，`GetChildren()` 全量枚举 vs 达到 `max_nodes` 就停的差异。

**任务集**（回答真实收效）：
| 场景 | 任务 | 独立判据 |
|---|---|---|
| 资源管理器 | 找到指定文件并读取大小 | 文件系统实际大小 |
| 记事本 | 定位编辑区、输入、回读 | 控件 `Value` 或 OCR |
| Windows 设置 | 找到指定开关并读状态 | 控件 `ToggleState` |
| 微信聊天 | 找到指定聊天 | 截图人工/OCR 复核 |
| 微信朋友圈 | 定位重复图标 | 截图复核 |
| 游戏/HUD | 跟踪一个目标 | 截图复核 |

每个任务记录：调用数、OCR 次数、UIA 读取次数、P50/P95 耗时、是否一次成功、失败重定位次数。**完成与否不看 `success=true`**，看上面第三列。

## 四、原则

每个阶段必须证明至少改善一项：准确率 / 执行延迟 / 调用数 / OCR 次数，且不显著损害其他项。做不到就回滚，不写进发布说明。

## 五、R0 基线（2026-11-14，本机 2560×1440）

`tools/bench/observe_bench.py`，depth 8，max_nodes 400，9 次取中位数。同一份 `_walk` 复制品，
分别只读 0/1/2/3/4 个属性，把"遍历"和"属性读取"拆开。

| 窗口 | 节点 | 纯遍历 | 全量读取 | 遍历占比 | 属性占比 |
|---|---|---|---|---|---|
| 资源管理器 | 279 | 78.4 ms | 129.9 ms | **60%** | 40% |
| 记事本 | 131 | 41.3 ms | 60.8 ms | **68%** | 32% |

单属性成本（资源管理器，279 节点）：Name +16.4 ms、BoundingRectangle +14.1 ms、
ControlTypeName +10.4 ms、**AutomationId +10.6 ms**。

宽父节点（29 个子项）：`GetChildren()` 5.09 ms，walker 只取前 10 个 3.44 ms（省 1.65 ms）。

### 结论

1. **遍历是大头（60–68%）**，只缓存属性最多解决四成——这正是"原生缓存先延后、但别指望属性优化翻倍"的数据依据。
2. **`AutomationId` 按需读取值 ~8%**（10.6 / 135.7 ms），低风险，先做。
3. **宽父节点早停**在小列表只省 1.6 ms，但按子项线性放大：500 项的列表约省 30 ms。
4. `ui_tree` 实测 135.7 ms，复制品 129.9 ms，误差 4%，可以拿复制品做 A/B。

## 六、任务级基线（v1.4.2，2560×1440，3 次中位数）

`tools/bench/task_bench.py`，失败判据独立于工具的 `success` 字段。

| 任务 | 通过 | 中位耗时 | 读到的节点 |
|---|---|---|---|
| 资源管理器整树 | 3/3 | 146.4 ms | 279 |
| 资源管理器找「地址栏」 | 3/3 | 134.1 ms | 2 |
| 记事本定位文档区 | 3/3 | 42.0 ms | 67 |
| 记事本找「文件」菜单 | 3/3 | 35.3 ms | 3 |

### 本轮发现（下一阶段要验证的假设）

**`ui_find("地址")` 花 134 ms，却只返回 2 个候选——和整树读取几乎同价。**

读源码确认：`ui_find` 先把整棵树走完（`_walk(max_nodes=400)`），再在结果里过滤，
中途从不提前停止。这意味着"找第一个匹配"的常见用法付了"读完整棵树"的代价。

R1 要验证的假设：**命中够数就停**能把这类调用降到 20–40 ms 量级。
若实测不成立，就如实写进结论，不改成"感觉快了"。

## 七、R1 结果（前后交替测量，3 轮 × 3 次）

`tools/bench/ab_runner.py`：同一进程里交替跑「已安装 1.4.2」和「.runtime 覆盖层」，
避免两次测量之间环境漂移。

| 任务 | 改前 | 改后 | 变化 |
|---|---|---|---|
| 资源管理器整树 | 140.8 ms | 139.6 ms | −0.9% |
| 资源管理器找「地址栏」 | 135.0 ms | 124.5 ms | **−7.8%** |
| 记事本定位文档区 | 42.6 ms | 43.0 ms | +0.9% |
| 记事本找「文件」菜单 | 35.4 ms | 33.1 ms | **−6.5%** |

`ui_tree(with_ids=False)` 单测：138.8 → 126.0 ms，**−9.2%**（AutomationId 每个控件一次跨进程调用）。

### 结论：有效，但远没有想象中大

命中就在树顶附近时（菜单）能省 6.5%；命中在深处时（地址栏）只省 7.8%——
**因为要到达命中点，仍然得把路径上的节点走一遍**。早停只砍掉"命中之后"的部分。

### 一条被数据否掉的方案：用库自带的原生搜索

`uiautomation` 的 `Control(SubName=...)` 底层是 `FindFirst`，看起来能把 120 ms 变 1 ms。
实测：**未命中 10.0 s、命中（depth=16）也 10.0 s 后抛 LookupError**——它内部按 10 秒超时轮询。
这条路径已删除，代码里留了注释说明为什么不用。要用原生搜索，必须绕开这个库、
直接用 comtypes 调 `IUIAutomation::ElementFindFirst` + `PropertyCondition`，属于 R4 之后的独立任务。

### 另一个观察

资源管理器的**文件列表项不在 UIA 树里**（279 个节点全是窗格/状态栏/查看模式，
连"4,759 个项目"都只是状态文本）。所以"按文件名在资源管理器里定位文件"这条路
在当前实现下走不通——这类界面只能靠坐标 + OCR，或者等以后补 VirtualizedItem 处理。
记在这里，避免以后又把"UIA 能覆盖资源管理器"当成既成事实。



## 八、R2 结果：模板跟踪（真机）

`match_template(previous=[x,y], radius=…)`：只在上次位置周围的方框里搜，返回 `moved_by`。
真机（资源管理器，模板取自地址栏 160×40）：

| 步骤 | 结果 |
|---|---|
| 首次匹配 | center=[440,260]，score 1.0 |
| 窗口移动 (+80,+60) 后跟踪 | center=[520,320]，**moved_by=[80,60]**（与窗口位移完全一致） |
| 跟踪耗时 | **53.3 ms** |
| 整窗搜索耗时 | 112.5 ms（**跟踪 −53%**） |

### 失效必须拒绝（POC 的重点，不是加分项）

| 情况 | 行为 |
|---|---|
| 分数低于 `confidence` | `found=false`，`reason=below_threshold` |
| 两处相似峰值（差 ≤ 0.02） | `found=false`，`reason=ambiguous`，给出 `peaks` 与 `second_score` |
| 跟踪框与窗口无交集 | **报错**，绝不"退化成搜整窗" |
| 搜索框比模板小 | 报错 |

### 顺带修掉一个真 bug

`match_template(hwnd=…)` 以前返回的是**窗口相对坐标**，文档却写"屏幕绝对坐标"——
窗口抓图的裁剪原点没有加回去。跟踪功能把它暴露了出来（第一次中心算错，跟踪框跑到错处）。
现在窗口抓图会把窗口原点加回，返回真·屏幕坐标。

## 十、没做的事（诚实清单）

| 项 | 为什么没做 |
|---|---|
| 原生 `ElementFindFirst` | 库的封装会 10 s 超时；要做得绕开库直接 comtypes，超出本轮范围 |
| 增量 `ui_tree(mode=delta)` | 只省传输不省遍历，身份配对是硬骨头，等有数据支撑再做 |
| `ui_read_table` / TextPattern | 与当前主要场景（微信/游戏）无关 |
| CDP 浏览器直连 | 同上，等有网页任务需求 |
| 事件驱动 `wait_for` | 收益明确但工作量独立，不在本轮 |
